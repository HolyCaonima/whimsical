# Dynamics：集合遍历与迭代调度重构

这次修改没有达到百万自由度、完整 tick 低于 4 ms 的目标，也没有显著加速原始的一万规模例子。保留下来的收益主要在百万规模：去掉逐行候选关系缓存后，暖机后的平均完整 GPU tick 从 270.6 ms 降到 164.4 ms，第 12 帧从 399.3 ms 降到 185.2 ms。不能把这个结果解释成已经获得了专用 GPU 解算器的效率。

## 保持的边界

- 用户的 `lab.js` 和 `fluid.js` 未修改；自由度、关系、残差、回缩函数仍由用户定义。
- 步长仍是 1/30，4 个 substeps，每个 12 次 iterations；compliance、边界、阻尼及自动微分的表达式没有替换。
- 编译器只识别集合映射、有限支撑、差分范数、线性化和所有权；没有添加具体物理对象类型、名称匹配或场景参数匹配。
- 没有改 RenderCore、没有使用 subagent、没有添加测试文件。运行的是已有测试和已有性能场景；百万观测脚本只追加了结果回读。

## 保留的编译器变化

`CollectionOperator` 原有的数学证明继续决定是否可以直接产生两个矩阵自由的运算：线性化，以及转置作用。`CollectionSolvePlan` 继续决定数值步骤。本次新增的 `CollectionTraversalPlan` 单独决定物理遍历形式和归约执行宽度。

对于拥有独立修正域的 projected-line-search 路径，当固定行缓存超过 8 MiB 的后端预算时，选择排序区间遍历。这个预算是初步的存储策略，不是经过所有设备验证的通用最优点。小集合继续使用原来的行缓存，其他求解策略保留原来的路径。

旧的大集合路径为每一行保留最多 128 个逻辑成员 ID，维护成员运动参考、行缓存版本和桶版本，并在消费时把逻辑 ID 再映射到物理位置。百万行光成员表就需要 512,000,000 字节，尚未计入其版本和运动参考。本次删除了这套持久行缓存及其失效协议。

新的大集合路径保留空间排序、桶起止位置和当前状态快照。在紧凑索引可用时，相邻 x 单元在排序中连续，因此三个相邻单元可以合并为一个连续区间：三维的 27 个单元查询变成至多 9 个区间遍历。生成的代码直接访问排序后的状态，执行用户表达式及其导数，不建立逐行成员表。当前实现使用一个 invocation 负责一行，空间排序使相邻输出能复用附近输入缓存。

运动有效性仍使用原有的 0.024R 位移界。单元宽度 1.0502R 覆盖两端累计的 0.048R；区间遍历再按已证明的支撑半径排除无贡献项。不能建立紧凑索引时，使用原有的哈希遍历；索引不可用时，保留完整枚举。这里没有邻居数量截断，也没有复用过期导数。

调度部分新增 `OwnerOutput`：一个逐自由度 producer 在最终写回之前，显式提供其所有者和寄存器中的结果。调度器只有在所有者域、步幅、宽度完全一致，且没有中间 apply/iteration 阶段时，才把本次迭代的末尾与下次迭代的逐所有者前缀组合。

```text
旧：L(q) → Jᵀd → 曲率归约 → 回缩并写回 → 下一轮所有者关系 → 发布快照
新：L(q) → Jᵀd → 曲率归约 → [回缩 → 下一轮所有者关系 → 发布快照]
```

这保持每个所有者的关系顺序，以及下轮的 iteration 参数。不同所有者之间仍然通过原有 GPU 阶段边界交换快照。不会跨 substep 组合。运动标记先在 workgroup 内归约，再发布一次全局标记；尾部无效 invocation 也参与相关 barrier。

## 测量结果

基线是修改前 `2856cbd` 的 Release 可执行文件。设备为 RTX 3080，开启 Vulkan validation。计时为完整 Dynamics GPU 提交区间，不包含渲染；表内性能比较关闭详细 profiler。百万场景采用仓库已有扩展脚本，同一用户表达式、参数和求解预算；它扩大了自由度数量与容器尺寸，不是原始一万场景的同一物理初始状态，也不是与外部专用解算器的同机对测。

| 场景和取样窗口 | 基线 | 保留版本 |
| --- | ---: | ---: |
| 一万，tick 31–180 平均 | 3.382 ms | 3.429 ms |
| 一万，1800 tick 中最后 180 tick 平均 | 4.030 ms | 3.885 ms |
| 百万，tick 2–12 平均 | 270.580 ms | 164.363 ms |
| 百万，tick 9–12 平均 | 355.190 ms | 179.809 ms |
| 百万，tick 12 | 399.255 ms | 185.220 ms |

一万的运动阶段没有改善，后段的变化也很小。百万的首帧从 221.676 ms 到 273.111 ms，存在首用开销回退；暖机均值没有包含首帧。百万只观察了 12 tick，不能据此宣称其长期稳定性能。

原始一万场景运行了 1800 tick，两个版本的 invalid/singular 计数均为零。第一帧最大坐标差为 1.91e-6。末帧密度超额均值分别为 0.001241 和 0.001239，P99 为 0.006211 和 0.006505；最大值为 0.02787 和 0.04001。末帧速度 RMS 为 0.003248 和 0.004190。并行枚举及归约顺序会改变浮点轨迹，因此不能声称逐点一致，也不能仅凭均值相近宣称所有质量指标无退化。

百万末帧对相同的 4096 个随机逻辑 ID 计算完整邻域密度，超额均值从 0.012619 到 0.012255，P99 从 0.091787 到 0.090251；两个版本的 invalid/singular 均为零。这是抽样观测，不是全域误差上界。

最后一份百万详细 GPU profile 中，线性化约 69.1 ms，转置及曲率计算约 61.2 ms，组合后的所有者更新约 26.7 ms，空间索引阶段合计约 25.5 ms。瓶颈已经从逐行候选表生成转移到这几个阶段；两次邻域遍历仍在每个 tick 中各执行 48 次。下一步必须减少每次访问的实际成本、进一步复用相邻输出的输入，或研究更有效的通用数值方法；只继续减少少量 dispatch 不足以跨越到 4 ms。这不是对 4 ms 不可能的证明。

## 没有保留的实验

试过 workgroup 共享候选块、subgroup 扁平查询、扩大候选缓存有效范围、相对坐标失效判断，以及查询与线性化融合。部分实验降低了某个阶段或静止阶段的时间，却增加整体时间或导致一万场景在运动阶段回退。它们没有保留在代码中，也没有用其中更好看的局部计时作为最终结果。

这些实验进一步说明：[Ebb](https://sing.stanford.edu/site/assets/publications/ebb-tog2016.pdf) 的隐藏排序和分组、[Simit](https://commit.csail.mit.edu/papers/2016/simit.pdf) 的所有者计算与中间量消除、[Taichi](https://yuanming.taichi.graphics/publication/2019-taichi/taichi-lang.pdf) 的局部输入复用，值得落实为可选择的物理执行形式，但不能仅根据“融合”或“shared memory”这些标签假定必然更快。
